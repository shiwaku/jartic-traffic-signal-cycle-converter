# 再設計メモ

現行実装（2026-08 時点）の設計上の問題と、作り直す方向。数値は 2026年6月分の実データ
（交差点 10,543 箇所 / 253,031 レコード）で実測したもの。

## 1. 現状と、症状の出どころ

```
JARTIC zip ──calc_average_cycle──> national_average_cycle.csv (259,938行)
TMT HTML  ──HTMLtoCSV──────────> intersection_position.csv
                └─csvfile-add-latlon─> signal_cycle.geojsonl (253,031 features / 61MB)
                                          └─tippecanoe─> signal_cycle.pmtiles (13.8MB)
                                                            └─ viewer: 時間帯=="07:00" で setFilter
```

困りごと（見た目・変更しづらさ・パフォーマンス・機能追加のしにくさ）は、根っこが2つしかない。

### 根っこ① 「1レコード = 交差点 × 時間帯」というデータモデル

同じ座標が24回書かれ、フィーチャ数が 10,543 → 253,031 に膨らんでいる。ここから、

* PMTiles が 13.8MB
* **低ズームでデータが消える（後述の既知バグ）**
* 時間帯を変えるたびに `setFilter` で全タイルのフィルタを再評価する
* 「その交差点の24時間の推移」がデータ上バラバラの地物なので、時系列を使う機能が作れない

が全部出ている。

### 既知バグ: ズーム7未満で 0 時以外が表示されない

現行の `signal_cycle.pmtiles` をズームごとに展開して数えた結果。

| ズーム | タイル内フィーチャ数 | 含まれる時間帯の種類 |
|---|---|---|
| z0 | 10,544 | 1（00:00 のみ） |
| z4 | 11,261 | 1（00:00 のみ） |
| z5 | 10,887 | 1（00:00 のみ） |
| z6 | 10,998 | 1（00:00 のみ） |
| z7 | 266,488 | 24 |
| z8 | 266,898 | 24 |

24レコードが完全に同じ座標を共有するため、`--drop-densest-as-needed` が低ズームで
「最も密な地物」＝同一座標の重複と判断して 23/24 を落とし、**各交差点で 00:00 だけが残る**。
結果、**ズーム6以下では時間帯スライダーを 0 時以外にすると点が1つも描かれない**。

全国表示はこのビューワの主役の画面なので、これは無視できない。wide 化はこの問題も同時に消す。

### 根っこ② 状態の置き場所が無い

`main.ts` 531行の中で、`hour` はモジュール変数、レイヤーの ON/不透明度は `layers.ts` の
`LayerDef` を直接書き換え（**定義とランタイム状態が同居**）、UI の DOM は `index.html` に
ハードコード。UI と地図が互いを直接書き換える双方向配線のため、機能を1つ足すたびに
配線が2本増える。

## 2. データモデル: long → wide

### 2.1 実データの裏取り

| 項目 | 値 |
|---|---|
| 結合済みレコード | 253,031 |
| 交差点 | 10,543 |
| 24時間帯すべて揃う交差点 | 10,542（23時間が1箇所のみ） |
| 24時間が全部同じ値の交差点 | 192（1.8%） |
| 日内変動（max−min）の中央値 | 35 秒 |

**24時間がほぼ完全に揃っている**（欠測は 10,543 件中 1 件）ので、wide 化で無駄な欠損列は
発生しない。また日内変動の中央値が 35 秒あり、時間帯別に見る価値があることも確かめられた。

### 2.2 新しい属性スキーマ

1交差点 = 1フィーチャ。

```jsonc
{"geometry": {"type":"Point","coordinates":[139.62,35.46]},
 "properties": {
   "src": "3010",       // 情報源コード
   "no":  "123",        // 交差点番号（情報源コード内の連番。文字列のまま）
   "c0": 118, "c1": 112, ... "c23": 120   // 時間帯別の平均サイクル長（整数秒）。欠測はキーごと省略
 }}
```

決めたこと:

* **属性キーは ASCII に短縮する。** 式（`['get','c7']`）が素直に書け、JS 側の扱いも楽。
  表示名は viewer 側の辞書で日本語に戻す。
* **`年月` はフィーチャから外す。** 全レコードで同一なので `dataset.json` に持たせる。
* **整数秒に丸める。** 現在は小数2桁で保持し表示で0.1秒に丸めている。1か月平均の 0.1 秒に
  意味は無く、整数の方が MVT の varint に乗る。
* **欠測はキーを省略する。** `['has','c7']` で判定でき、null を式で扱わずに済む。
* **派生値（cmin/cmax/cavg/cpeak）はタイルに入れない。** 計測したところ 5 つ足すと z13 で
  4.95MB → 5.66MB と 0.7MB 増える。24 個の値が手元にあれば JS で即座に計算できるので、
  タイルに載せる必要が無い。品質ゲート用の集計はパイプライン側で計算して
  `dataset.json` に書く。

#### 検討して**採らなかった**案: 24時間を1本の文字列にする

`"cy": "118,112,...,120"` にすると string pool の重複排除が効き、z13 で 4.52MB と最小に
なった（−0.4MB）。しかし **MapLibre の式から時間帯別の値を取り出せなくなり**、
`setPaintProperty` で色を切り替える設計が成立しない。0.4MB のために主目的を捨てる形に
なるため却下。

### 2.3 実測した効果

`tippecanoe -Z0 -z13 -r1 --drop-densest-as-needed` で比較。

| | 現在（long, z14） | wide, z13 |
|---|---|---|
| features | 253,031 | 10,543 |
| GeoJSONL | 61.0 MB | **5.0 MB** |
| PMTiles | 13.8 MB | **4.95 MB（−64%）** |
| z0 に載るフィーチャ | 10,544（96%が脱落） | **10,546（全点）** |
| z0〜z6 で使える時間帯 | 00:00 のみ | **全24時間帯** |
| 時間帯切替 | `setFilter` → 全タイル再評価 | `setPaintProperty` で `['get','c7']` に差し替え |
| 24時間の推移 | 取れない | 1フィーチャに入っている |

zoom 上限別のサイズも測った。z12: 4.75MB / z13: 5.66MB / z14: 6.99MB（いずれも派生値ありの
数値）。**z13 を採る。** z13 の座標精度は約1.2mで交差点の位置には十分であり、z14 との差
1.3MB に見合わない。

`--drop-densest-as-needed` は残すが、wide 化後は z0 でも全 10,543 点が残る（実測）ので
実質発動しない。将来交差点が増えたときの保険として置いておく。

```
tippecanoe -o signal_cycle.pmtiles -l signal_cycle -Z0 -z13 -r1 \
           --drop-densest-as-needed --force -P signal_cycle.geojsonl
```

## 3. 配色

### 3.1 実データの分布

```
 p1 = 70    p25 = 102    p50 = 120    p75 = 140    p95 = 160    p99 = 180
 min = 50   max = 255
```

現行の段階配色は 100〜160 秒に8段を割り当てている。つまり **p24 未満（全体の24%）が
すべて同じ青、p95 超（5%）がすべて同じ赤**で、都市部と地方の違いは出るが、その内側の差が
潰れている。

### 3.2 新しい配色

**知覚均等な連続配色（plasma 系）に変える。** 明度が単調に増えるので「明るいほど長い」が
直感になり、色覚特性が異なる場合やグレースケールでも順序が読める。

* **ドメインは 70〜180 秒（p1〜p99）、両端はクランプ。** 実データの分布に合わせる。
  月ごとに変えると月間比較ができなくなるので**固定値**とし、分布が外れたら品質ゲートで気づく。
* **テーマで明度レンジを変える。** 色相の進みは共通のまま、背景とのコントラストを保つ:
  * ライト（淡色地図）: plasma 0.00〜0.85（濃紺 → マゼンタ → オレンジ）。淡い黄色は使わない。
  * ダーク: plasma 0.15〜1.00（紫 → オレンジ → 黄）。ほぼ黒の暗端を使わない。
* 中心の白い芯（`signal-core`）は維持する。暗端の点でも位置が分かる。
* 凡例は8段のリストをやめ、**連続グラデーションバー + 目盛り（70/120/180秒）**に。
  さらに**現在時間帯の分布ヒストグラム**を重ねると、「今の時間帯は全国的に長いのか」が
  一目で分かる。

### 3.3 円の半径

現在 `circle-radius` はズームによらず固定（glow=18px）で、全国表示では巨大な塊になる。
ズーム補間に変える。

```js
'circle-radius': ['interpolate', ['linear'], ['zoom'], 4, 3, 9, 9, 14, 18]
```

### 3.4 時間帯切替

`setFilter` をやめ、paint プロパティの差し替えにする。欠測時間帯は不透明度0で消す
（フィルタを触らないのでタイルの再評価が起きない）。

```js
map.setPaintProperty('signal-mid', 'circle-color',
  ['interpolate', ['linear'], ['get', `c${h}`], ...STOPS])
map.setPaintProperty('signal-mid', 'circle-opacity',
  ['case', ['has', `c${h}`], base * userOpacity, 0])
```

### 4.1 状態

```ts
export interface AppState {
  hour: number                        // 0-23
  playing: boolean
  theme: 'light' | 'dark'
  basemap: 'pale' | 'photo'
  layers: Record<LayerKey, { visible: boolean; opacity: number }>
  selection: { key: LayerKey; src: string; no: string } | null
}
```

`get()` / `set(patch)` / `subscribe(fn)` だけの小さなストア（40行程度）。フレームワークは
入れない（依存を増やさず PWA を軽く保つ）。**UI も地図も state を購読するだけ**にして、
`def.on = x` のような定義の書き換えをやめる。

レイヤー追加が「`layers/xxx.ts` を1枚足して registry に1行」で済む形にする。

### 4.2 URL 状態

現在は MapLibre の `hash: true` で地図位置だけが URL に載る。時間帯・レイヤー・テーマ・背景も
クエリに載せ、「朝7時の名古屋」を共有できるようにする。

```
?h=7&l=signal,did&t=dark&b=photo#12/35.17/136.90
```

### 4.3 ベースマップスタイル

`pale-style.json`（354KB）を JS バンドルに取り込み、ダークテーマは実行時に
`structuredClone` + 全レイヤー走査で生成している。**ビルド時に light / dark 両方のスタイル
JSON を生成して静的アセットにし、fetch で読む**。初期バンドルが軽くなり、テーマ切替も速い。

## 5. UI/UX

### 5.1 現状の問題

* **一番使う「時間帯」が折り畳みパネルの中にある。** モバイルは初期状態で畳まれるので、
  パネルを開くまでスライダーに触れない。
* **凡例8段が常時展開**でパネルが縦に長い。
* **`情報源コード: 3010` が生で出る。** `data/source_names.json`（「埼玉」等）が既にあるのに
  ビューワから使われていない。
* レイヤー2枚に対する「全ON/全OFF」は過剰。
* ポップアップは単一時間帯の値しか出せない（データモデルの制約）。

### 5.2 新しいレイアウト

```
デスクトップ
```

## 6. パイプライン

### 6.1 現状の問題

* 命名がケバブ / パスカル / スネークで混在し（`csvfile-add-latlon.py`, `HTMLtoCSV.py`）、
  Python から `import` できない。したがってユニットテストが書けない（テスト0件）。
* `csvfile-add-latlon.py` が「結合」「GeoJSON生成」「レポート生成」の3役を持ち、
  average CSV を3回読んでいる。
* カタログ解決・UA・リトライが `run_pipeline.py` と `jartic_opendata_kousaten_dl.py` に重複。
* 途中再開が `--skip-download` しか無く、後段で落ちると20分やり直しになりがち。
* スクリプト間の契約が「work/ 配下のファイル名」という暗黙の取り決めで、`run_pipeline.py` に
  散らばっている。

### 6.2 新しい構成

```
src/jartic_signal/
  paths.py      work/ 配下のファイル名の契約を集約
  catalog.py    カタログ解決（fetch / normalize_month / normalize_day）
  fetch.py      zip・HTML のダウンロード（共通のリトライと UA）
  cycle.py      zip → 時間帯別集計
  position.py   HTML → 座標（ページ↔情報源コードの割当を含む）
  join.py       結合 → wide レコード + 結合レポート
  tiles.py      geojsonl 書き出し + tippecanoe 呼び出し
  gate.py       品質ゲート（純関数）
  report.py     dataset.json / README の生成
  cli.py        薄い CLI（check / run / ステージ個別）
tests/
  test_gate.py      ゲート判定（小さな固定入力）
  test_position.py  ページ↔情報源コードの割当（北海道5方面）
  test_cycle.py     zip 集計（小さな zip をその場で作る）
```

各ステージは「入力パス → 出力パス」の関数にし、CLI は薄く保つ。ステージごとに work/ へ
チェックポイントを置き、`run --from join` で途中再開できるようにする。

### 6.3 品質ゲートの強化

現在の4項目に、値の妥当性を見る判定を足す。今は「サイクル長が0秒」「座標が海の上」の
ようなデータが素通りする。

| 判定 | 内容 | 現状 |
|---|---|---|
| 対象年月 | 前回より新しくない | あり |
| 交差点数 | 前回比 −5% 超 | あり |
| 行の結合率 | 前回比 −2pt 超 | あり |
| 情報源コード | 位置情報が1件も結合できないコードがある | あり |
| **サイクル長の中央値** | **前回比 ±10秒 超**（今回の実測値 120秒） | 追加 |
| **値域** | **30〜400秒の外に出るレコードが 0.1% 超**（今回 50〜255秒） | 追加 |
| **時間帯の網羅** | **24時間帯が揃わない交差点が 1% 超**（今回 1/10,543） | 追加 |
| **座標の範囲** | **日本の bbox（122〜154E, 20〜46N）の外にある点がある** | 追加 |
| **タイルサイズ** | **前回比 ±50% 超** | 追加 |

生 zip のアーカイブを品質ゲートより先に済ませる現在の判断（JARTIC は最新1か月分しか
配布しないため）は正しいので、そのまま維持する。
